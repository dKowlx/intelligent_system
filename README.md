# Project Navigator

Веб-приложение для индивидуальных учебных, рабочих и личных проектов.
Преобразует материалы в редактируемую карточку и действия, рассчитывает
расписание по доступному времени, сохраняет прогресс и историю разговоров.
Техническое имя Python-пакета — `studynavigator`.

- [Сервис](https://navigator.136-234-80-52.sslip.io/)
- [Репозиторий](https://github.com/dKowlx/intelligent_system)

## 1. Задача

Приложение связывает требования проекта с действиями, ожидаемым результатом
и признаком готовности. Для действий сохраняются оценки времени, их основания,
зависимости и приоритеты. Планировщик распределяет оставшуюся работу по дням
и показывает работу, которая не помещается в доступный бюджет.

Сведения из материалов и дополнения пользователя имеют отдельное происхождение.
Неизвестный срок хранится как `null`. Оценки длительности и фактическое время
хранятся раздельно; отметку готовности устанавливает пользователь.

## 2. Пользователь и сценарий

Пользователь ведёт индивидуальный проект с ограниченной доступностью по дням.

1. Создаёт проект из текста или загружает PDF.
2. Запускает AI-анализ либо заполняет карточку вручную.
3. Подтверждает цель, результат, требования, критерии и срок.
4. Редактирует действия, подшаги, результаты, оценки и зависимости.
5. Задаёт доступность по дням и резерв; сохраняет рассчитанный план.
6. Отмечает завершение и фактическое время, пересчитывает остаток работы.
7. Обсуждает материалы и план с ассистентом, открывает источники ответов.
8. Подключает локальный Codex к проекту с выбранными правами: получает отчёты,
   синхронизирует прогресс подшагов, время и план; выбирает проверку или автозавершение.

Интерфейс содержит разделы «О проекте», «Ассистент», «Обзор»,
«Действия и план» и «Аналитика». Маршрут представлен схемой зависимостей
или списком. Доступны светлая, тёмная и системная темы.

Материалы проекта можно дополнять текстом, PDF и ссылками на статьи
с сохранённым текстом. Содержимое URL автоматически не загружается.
История разговоров хранится на сервере; пользователь выбирает, создаёт
и удаляет разговоры в пределах проекта.

## 3. Границы MVP

| Область | Реализация |
|---|---|
| Материалы | Текст, PDF, фрагменты, поиск и просмотр оригинала |
| Карточка | Цель, результат, требования, критерии, срок и происхождение |
| Действия | Подшаги, результат, готовность, оценки, приоритеты и зависимости |
| План | Дневные бюджеты, резерв, дефицит, учёт завершённых действий |
| Прогресс | Отметки, фактическое время, снимки и аналитика |
| Ассистент | Ответы с источниками и изменения плана с отдельным применением |
| Codex | Ключ проекта с правами и сроком, отчёты, прогресс подшагов, факт времени и изменение плана |
| Хранение | SQLite, файлы загрузок и серверная история разговоров |

Загрузка ограничена 1–3 PDF, 10 MiB суммарно, 100 страницами
и 100 000 извлечённых символов с учётом текстовых материалов проекта.
Нужен текстовый слой; OCR, DOCX и сканы не поддерживаются.

В MVP нет командной работы, аккаунтов, календарной синхронизации,
уведомлений и интеграции с LMS. Доступ разделён анонимной браузерной cookie.
Восстановление доступа после её утраты не предусмотрено.

Расписание задаёт минуты работы по дням, а не часы начала и окончания.
Структурная связь с требованием не подтверждает качество готового результата.

## 4. Архитектура

Стек: Python 3.12, FastAPI, Pydantic, SQLite/FTS5, pypdf,
HTML, CSS и JavaScript. Зависимости зафиксированы в `uv.lock`.

```text
Браузер → FastAPI → SQLite и файлы материалов
              ↓
          AI-логика → MCP-клиент → MCP-сервер → материалы
              ↓
          API модели → проверка ответа → браузер
```

Backend проверяет схемы, источники, версии записей и зависимости.
Python рассчитывает суммы, дневные бюджеты и дефицит.
Резерв вычитается из бюджета каждого дня с округлением вниз.
При известной дате начала учитывается срок проекта.

Карточки, планы и прогресс сохраняются с версиями. Конфликтующие изменения
отклоняются. Изменение карточки делает прежний план устаревшим.
Фактические минуты сами по себе не уменьшают оценку оставшейся работы.
API-ключи остаются на сервере.

## 5. MCP-интеграция

Собственные клиент `studynavigator/mcp_gateway.py` и сервер
`studynavigator/mcp_server.py` используют MCP Python SDK и транспорт stdio.

| Инструмент | Назначение |
|---|---|
| `list_assignments` | Список доступных проектов |
| `get_assignment` | Карточка, факты, источники и контекст проекта |
| `search_materials` | Поиск материалов; дополнительные исследования и теория |

Инструменты читают данные. Область доступа задаётся серверным контекстом
браузерной сессии; модель не выбирает владельца проекта.
Клиент проверяет аргументы, ответы, тайм-ауты и допустимые имена инструментов.

Для загруженного проекта с Yandex/DeepSeek чтение материалов инициирует
приложение до запроса модели. Для подготовленного примера поддерживается
ограниченный цикл выбора инструментов моделью. Оба пути используют MCP.

Локальный Codex подключается отдельным stdio-мостом `studynavigator/codex_bridge.py`
к HTTPS API сайта. Инструменты `get_project`, `search_materials`, `claim_task`,
`report_task`, `update_progress` и `update_plan` читают проект и синхронизируют
работу в пределах прав `read`, `reports`, `progress`, `plan`. Ключ ограничен одним
проектом, действует 1–30 дней и хранится на сервере только в виде хеша. Режим
`review` требует проверки результата владельцем; `auto` с правом прогресса
разрешает завершение агентом с описанием и подтверждениями. Старые ключи не
получают новых прав: их нужно перевыпустить. Действия и подшаги сохраняют
завершение и время по ID; версии и `request_id` защищают от устаревшей записи
и повторного применения изменения. Владелец может исправить прогресс и отозвать ключ.

Фактическое время явно разделено по источнику: пользовательский итог (например,
ровно 200 минут), добавляемый измеренный активный интервал, отдельная оценка
агента или неизвестное `null`. Монотонный таймер моста включается явным
`start`/`resume` и останавливается при паузе или отчёте; сеть и разрыв процесса
не начисляются. Перед внешним ожиданием агент явно ставит паузу. Аналитика
показывает факт подшагов без повторного суммирования с явным итогом родителя.

[Инструкция подключения для пользователей](docs/codex-connection.md).
Каждый пользователь выпускает свой ключ и отдельно разрешает Codex работу
в своём локальном репозитории. Сайт не получает доступ к файловой системе,
Git или учётной записи Codex пользователя.

## 6. AI-логика

Адаптер использует API Chat Completions. Модель задаётся через `LLM_MODEL`;
`LLM_ANALYSIS_MODEL` позволяет отдельно настроить анализ материалов.
Опубликованная конфигурация использует DeepSeek V4.1 Flash/latest.

AI-анализ возвращает карточку с требованиями и действиями.
Действие содержит результат, критерий готовности, основание времени,
необязательный диапазон, приоритет и зависимости. Подшаги имеют свои минуты.
Схемы ответа и ссылки на доступные источники проверяются backend.

Чат получает материалы через MCP и возвращает ответ со ссылками.
По явному запросу ассистент формирует изменение плана. Отдельное применение
по одноразовому токену и версиям сохраняет изменения атомарно.
Однозначные команды длительности обрабатываются без вызова модели.

Общая серверная библиотека исследований использует SQLite, FTS5
и cosine similarity по Text Embeddings v2 doc/query размерности 768.
При недоступности embeddings используется FTS5 с признаком degraded status.
Индекс создаётся отдельно и не перестраивается при запуске приложения.
Исследования не становятся требованиями проекта.

Поиск общей теории использует MediaWiki API; выдержки сохраняются
с происхождением и ссылкой. Упомянутый, но не загруженный материал
не считается доступным источником.

В `offline` используются детерминированные ответы и настоящий MCP.
В `live` необходим настроенный провайдер. Ошибки live-запросов возвращаются
явно и не заменяются offline-ответами. Материалы трактуются как данные.

## 7. Запуск и размещение

Требуются Python 3.12 и `uv`. Из корня проекта:

```sh
uv sync --locked --extra dev
.venv/bin/python -m studynavigator
```

Адрес: http://127.0.0.1:8000/. По умолчанию включён `offline`.
SQLite создаётся в `var/study.db`, загрузки — в `var/uploads`.

Для `live` создайте отдельный `.env` по `.env.example` и задайте
`STUDYNAV_MODE=live`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`.

```sh
uv run --locked --extra dev --env-file .env python -m studynavigator
```

Обычный `python -m studynavigator` сам `.env` не загружает.
Файл с ключами не включается в репозиторий.
Пути задаются через `STUDYNAV_DB_PATH` и `STUDYNAV_UPLOADS_PATH`;
адрес и порт — через `HOST` и `PORT`.

Для библиотеки исследований предусмотрены `STUDYNAV_KNOWLEDGE_ROOT`,
`STUDYNAV_KNOWLEDGE_DB_PATH`, `EMBEDDING_BASE_URL`, `EMBEDDING_DOC_MODEL`,
`EMBEDDING_QUERY_MODEL` и `EMBEDDING_DIMENSIONS`.

Размещение использует Docker Compose и Caddy HTTPS. Конфигурация находится
в `compose.yaml`, дополнительная библиотека — в `compose.knowledge.yaml`.
Backend работает с одним worker и постоянным томом данных.
Конфигурация окружения передаётся отдельно от образа.
Для серверного домена задайте `DOMAIN` явно.

## 8. Проверки и исправления

```sh
.venv/bin/python -m pytest tests/app -q
node --test tests/web/*.cjs
.venv/bin/python tools/run_app_eval.py --output var/eval-offline.json
.venv/bin/python tools/check_hosted.py https://navigator.136-234-80-52.sslip.io
```

Тесты покрывают API, MCP, расчёт расписания и интерфейс.
Offline Eval содержит 30 случаев; offline и mock выполняются без подключённой модели.
HTTP-проверка доступности проверяет опубликованный сервис отдельно.

В новом проекте на опубликованном сервисе обработан документ «Личный проект.pdf»:
получены 7 требований, 5 критериев, 5 связанных действий и 17 подшагов.
Карточка подтверждена без ручного изменения ответа модели; расписание рассчитано
и сохранено на сервере. Основные технические результаты из предварительного
списка требований присутствуют в карточке и действиях. Неизвестный срок оставлен пустым.

В реализации исправлены дублирование действий в контексте чата,
обработка короткого подтверждения длительности и сохранение прогресса
независимо от редактирования карточки. Применение предложений проверяет
версии; старые сообщения истории не содержат действующего токена применения.
Проверки покрывают изоляцию материалов, MCP, расчёт расписания,
источники, конфликты записей и состояния интерфейса.
